# Codebase Conventions for AI Assistants

This supplements [README.md](README.md) (frameworks, dev commands, deploy) with code-level conventions the README doesn't cover. Read the README first. This repo is **independent** — no database, no env vars, no backend of any kind.

## SEO metadata: layout files exist to attach `metadata`

Most pages are client components (`'use client'`) and so can't export Next's `metadata` object themselves. The workaround used throughout: a thin server-component `layout.tsx` next to the page whose only job is `export const metadata = constructSEO({ title, description, image?, noIndex? })` (helper in `lib/seo.ts`), wrapping `children` with no other markup — see `app/faq/layout.tsx`, `app/reports/layout.tsx`, `app/testimonials/layout.tsx`. **Any new client-component page that needs custom SEO needs this same layout-file pattern**, not a `generateMetadata` function. There are no `generateMetadata` functions anywhere in the repo — all metadata is static per route.

## Bootstrap and Tailwind are mixed freely, not separated by rule

Existing components combine react-bootstrap components/utility classes (`<Row>`/`<Col>`, `display-3 fw-semibold d-flex gap-3`) and Tailwind classes (including arbitrary values and `!important` suffixes like `pt-[1rem]!`) in the same `className`, sometimes in the same component (see `components/home/HeroSection.tsx` vs `components/ClassPage.tsx`). There's no documented split — new layout/spacing work trends Tailwind, grid/interactive widgets trend react-bootstrap. Don't try to "clean up" this mixing as a side effect of an unrelated change.

## Two different content patterns — match the one that fits

- **Repeated, structured content** (FAQ, team bios, testimonials): centralized data array in `lib/` (`faqData.tsx`, `teamMembers.ts`, `testimonialsData.ts`) consumed by one generic component. Add new entries here, don't hand-code them into a page.
- **Course/track pages** (`app/cs/python1/page.tsx`, `app/math/math1a/page.tsx`, etc.): each page hand-declares its own `title`/`color`/`description`/`modules`/`slides` as top-level consts and passes them as props into the shared `ClassPage`/`TrackPage` component. **To add a new course page, copy an existing sibling page and edit its consts** — don't invent a new centralized data file for courses; that's not how this content type is organized.

`lib/courses.json` is not an exception to that: **nothing on the site reads it**, and no page should start to. It is a verbatim copy of the admin repo's `src/lib/data/courses.json`, the shared catalog of which courses gbSTEM offers that admin, portal and curriculum all copy, and it is here purely so `__tests__/courses.test.tsx` can hold this site to it. Admin and portal read the catalog at runtime and curriculum's own test fails when a course has no page there, so the public site was the one copy nothing checked — a course could be registerable in the portal and unmentioned on gbstem.org for a whole semester. The test's `COURSE_PAGES` table maps each catalog id to the URL that advertises it, and fails in both directions: a course added in admin fails until it is listed, and a listing whose course is gone fails too. It also checks that each mapped URL has a real `page.tsx` and that its track page links to it, since a page nothing links to is as invisible as a missing one. **So adding a course is four things, not one**: the page under `app/<track>/`, a link from its track page's `ClassProgression`, both the fall (`…A`) and spring (`…B`) ids in `COURSE_PAGES`, and — in the admin repo, which owns the file — the catalog entries themselves. Replace `lib/courses.json` wholesale at a rollover (`cp ../admin/src/lib/data/courses.json lib/courses.json`); never hand-edit an entry, and never add a website-only field. `.github/workflows/shared-data.yml` diffs both this file and `lib/semesterDates.json` against admin on every PR and nightly, so a hand-edit or a skipped copy step fails CI rather than going unnoticed.

Semester dates live in `lib/semesterDates.json` — **a verbatim copy of the admin repo's `src/lib/data/semesterDates.json`**, the shared source of truth that the admin, portal, and website repos all read so they never disagree about a date. It is replaced wholesale at each semester rollover (see "Adding a New Semester" in the admin repo's README); don't hand-edit a single field here, and don't add a website-only field — the next rollover's copy would overwrite it. `lib/constants.ts` parses that JSON into `Date` objects (`SEMESTER_START_DATE`, `REGISTRATION_ENDS_DATE`, ...), which are static and safe at module scope. Everything that depends on _when you ask_ comes from **`currentSemesterStatus()`**, which you must call **inside a component body, never at module scope**. That rule is the whole point: the site is statically prerendered (`yarn build` marks every route "prerendered as static content"), and module scope runs once per process, so the previous module-scope consts (`export const REGISTRATION_OPEN = new Date() >= ...`) were frozen into the HTML on deploy day and only corrected after the client bundle rehydrated - a visitor saw deploy-day copy until then. Re-rendering does not re-run module scope, so no revalidation setting can fix a value computed there. The returned status carries two kinds of condition, which are not interchangeable. The **booleans** (`registrationOpen`, `instructorAppsOpen`, `semesterInProgress`, ...) answer "is this window open right now?" and can overlap - use them to gate a link, a button, or a card. **`phase`** is a five-value union (`before-registration` | `registration-open` | `registration-closed` | `classes-in-progress` | `semester-over`) that is mutually exclusive and exhaustive - `switch` on it for any prose describing where the semester stands, so a page renders exactly one message and never zero. Rendering a paragraph per boolean instead is a known trap: it once produced two contradictory messages on the day registration closed and an empty alert box for the six days between Spring 2026's registration deadline and its first day of classes. `semesterStatusOn(date)` and `semesterPhaseOn(date)` are the pure versions, so tests can walk a whole calendar year. `app/layout.tsx` sets `revalidate` so the prerendered HTML is regenerated rather than frozen until the next deploy; `components/Navigation.tsx` renders there and shows date-dependent links on every route. The file also holds the external links, `CURRENT_SEMESTER`/`NEXT_SEMESTER` season labels, and the `formatDate` prose helper. Reuse those exports rather than re-hardcoding a date or link - `lib/faqData.tsx` and `components/home/Intro.tsx` are the examples to copy. `__tests__/constants.test.ts` validates the copied JSON's shape, so a malformed or mis-copied date fails `yarn test` instead of rendering "Invalid Date" in production.

**Every signup call to action gates on `registrationOpen`, and none of them writes its own href.** Open, they go to `GBSTEM_SIGNUP`; closed, to `MAILING_LIST_FORM_LINK` ("get notified"), so the site flips on the dates in `semesterDates.json` with no deploy on either day. `components/RegisterButton.tsx` is the whole of that for the course pages - `ClassPage` renders it and takes no link prop, so a new course page gets the behaviour for free and has nothing to hardcode. It is a client component, like `Navigation` and `HeroSection`, so hydration corrects it in the browser instead of leaving it as stale as the last revalidation; a date-dependent CTA rendered only on the server is the trap here. Note `registrationOpen` is bounded at **both** ends: a CTA wired to turn on and never off keeps sending parents to a portal that has stopped accepting them. `__tests__/RegisterButton.test.tsx` is the pattern to copy for testing one - it moves the system clock and reads the real dates rather than `jest.mock`ing `@/lib/constants`, because a mocked calendar keeps passing when a button is wired to the wrong field.

## Component conventions

`components/` is flat for site-wide pieces (`Footer.tsx`, `Navigation.tsx`, `ClassPage.tsx`, ...) with subfolders per page area for one-off sections (`components/home/`, `components/team/`, `components/donate/`). Props are typed via an adjacent `interface XProps { ... }` above the component, not inline-destructured types.

## Types

`@/*` maps to the repo root (`tsconfig.json`); `strict: true`; Cypress files are excluded from the main `tsconfig.json`.

## Lint is stricter than usual

ESLint (`eslint.config.mjs`) includes `eslint-plugin-prettier`, so **Prettier formatting violations fail `yarn lint`**, not just `yarn format` — don't assume lint and format are independent concerns.

## Testing

Jest + React Testing Library, `__tests__/*.test.tsx` named after the component/page under test. Pages/components are imported and rendered directly (`import Faq from '@/app/faq/page'`) with no routing or data-fetch mocking, since there's no backend — assertions use `screen.getByRole`/`getByText` and structural matchers like `toHaveStyle`/`toHaveAttribute`. `describe('<Name> Component'|'<Name> Page', ...)` / `it('renders ...')` naming.

## Misc gotcha

Image paths under `public/images/` include a directory literally named `penguin tiers` (with a space) — don't assume kebab-case for every asset folder.
